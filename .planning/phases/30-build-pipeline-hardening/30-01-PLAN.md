<objective>
Establish the three-file Node version pin (`.nvmrc`, `package.json` `engines.node`,
`eas.json` `build.production.node`) at one exact patch version, and regenerate
`package-lock.json` cleanly under that version with the full local verification
suite green.

Purpose: close the Node/npm drift that has caused three separate EAS `npm ci`
failures (v0.5 Phase 20, Phase 24, v0.6 Phase 29) by making the version explicit
in every location local tooling and EAS Build read.

Output: `.nvmrc` (new), `package.json` `engines` block (new), `eas.json`
`build.production.node` (new), regenerated `package-lock.json`.

**IMPORTANT — the version pinned by this plan is PROVISIONAL.** Per RESEARCH.md
Pitfall 1, the version `nvm install 22` resolves to locally (22.23.2 at research
time) may be one patch ahead of the Node version the real EAS build image actually
ships (22.23.1 at research time). Plan 30-02 runs the real production build and
reconciles the pin against the build log. Do NOT treat this plan's value as final,
and do NOT mark BUILD-01/BUILD-04 satisfied from this plan alone.
</objective>

<task type="auto">
  <name>Task 1: Resolve exact Node 22 patch and write the three-file pin</name>
  <files>.nvmrc, package.json, eas.json</files>
  <action>
Resolve the exact Node patch by running, in a single bash invocation (nvm is a
shell function and must be sourced each time — the working directory and shell
state do not persist between Bash tool calls):
`export NVM_DIR="$HOME/.nvm" && source "$NVM_DIR/nvm.sh" && nvm install 22 && nvm use 22 && node -v && npm -v`

Capture the exact `node -v` output and strip the leading `v` to get the bare
version string (e.g. `22.23.2`). This is the PROVISIONAL pin per D-02's "known
gap" — record both the bare version and the npm version reported alongside it in
the summary, because plan 30-02 reconciles this against the real build log.

Do not use the machine's default Node (v25.0.0 / npm 11.17.0) — per CONTEXT.md's
Specific Ideas, that is the drift source, not the target.

Write all three pins to that one exact string, per D-02 (exact patch, never a
floating major like `"22"` or `"22.x"`):

1. Create `.nvmrc` at repo root containing only the bare fully-qualified
   `major.minor.patch` string plus a trailing newline — no `v` prefix, no
   abbreviation. RESEARCH.md Pattern 2 (eas-cli issue #1975) confirms abbreviated
   forms like `v22` are rejected by eas-cli's `.nvmrc` parser.
2. Add a top-level `"engines": { "node": "<version>" }` block to `package.json`
   (per BUILD-02). Place it after the existing `"version"` key to keep the diff
   readable. Do not add an `engine-strict` setting or an `.npmrc` — RESEARCH.md
   assumption A3 confirms none exists and none is required.
3. Add `"node": "<version>"` to `eas.json`'s `build.production` object as a
   sibling of `autoIncrement` (per BUILD-03 and RESEARCH.md Pitfall 3). Do NOT
   add the field to `development`, `preview`, or a new `base` profile — CONTEXT.md
   and SC3 scope this to `production` only, and restructuring other profiles is
   out of scope.

Do not add any preflight/version-guard script — RESEARCH.md's "Don't Hand-Roll"
section explicitly rules that out as scope creep beyond BUILD-01..04.
  </action>
  <verify>
    <automated>export NVM_DIR="$HOME/.nvm" && source "$NVM_DIR/nvm.sh" && nvm use && V=$(cat .nvmrc | tr -d ' \n') && test "$V" = "$(node -v | sed 's/^v//')" && node -e "const fs=require('fs');const v=fs.readFileSync('.nvmrc','utf8').trim();const p=JSON.parse(fs.readFileSync('package.json','utf8'));const e=JSON.parse(fs.readFileSync('eas.json','utf8'));if(!/^22\.\d+\.\d+$/.test(v))throw new Error('nvmrc not an exact 22.x patch: '+v);if(p.engines?.node!==v)throw new Error('engines.node mismatch: '+p.engines?.node);if(e.build?.production?.node!==v)throw new Error('eas.json build.production.node mismatch: '+e.build?.production?.node);console.log('pin agreement OK: '+v)"</automated>
  </verify>

</task>

<task type="auto">
  <name>Task 2: Regenerate package-lock.json clean and run the full verification suite under the pin</name>
  <files>package-lock.json</files>
  <action>
Per D-03, in a single bash invocation with nvm sourced and the pinned version
active (`export NVM_DIR="$HOME/.nvm" && source "$NVM_DIR/nvm.sh" && nvm use`),
regenerate the lockfile completely clean:
`rm -rf node_modules package-lock.json && npm install`

Then run the proof sequence under that same Node version:
`npm ci --include=dev && npm run typecheck && npm run lint && npm test`

`npm ci` (not `npm install`) is the load-bearing check — per RESEARCH.md Pitfall 2,
`npm install` is permissive enough to hide exactly the mismatch that failed on
EAS's server in Phase 24 and Phase 29.

Expect a large `package-lock.json` diff: the lockfile was last written under npm
11 and is being rewritten under the npm 10.x that Node 22 bundles, so a
`lockfileVersion` change and shifting `os`/`cpu`/`libc` fields are normal here.
RESEARCH.md Pitfall 2 flags that diff shape as the signature of npm-version-driven
divergence — which is precisely what this phase is deliberately resolving, not a
regression. Note the observed `lockfileVersion` before and after in the summary.

If `npm ci` fails, do not work around it by falling back to `npm install` — the
failure is the bug this phase exists to close. Report the exact error and stop.

Leave the machine on the pinned Node version at the end of this plan; plan 30-02's
EAS build should run from the same environment. Do not switch back to the default
Node yet.
  </action>
