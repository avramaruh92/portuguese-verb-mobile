# Phase 10.1: Close Gap: UI-03 — Offline Content Indicator - Context

**Gathered:** 2026-07-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the v0.1 milestone audit gap on UI-03: surface a small, non-blocking,
session-wide "using saved content" indicator on all 3 screens (Setup, Quiz,
Results) whenever the dataset source resolved by Phase 7's `resolveVerbs()`
is `"local"` (i.e. the live backend fetch failed or was unreachable, and the
app silently fell back to the bundled dataset). This is a deliberate,
explicit pull-forward of **FETCH-05** (previously deferred to v2/P2) — see
`<canonical_refs>` for the audit and prior-decision trail this reverses.

Does NOT touch: FETCH-03's silent-fallback *behavior* (still never blocks,
never throws a user-facing error) — this phase only adds a passive,
informational visual signal on top of that existing silence. Does NOT add a
new error state, does NOT change `useQuizStore`'s `status` state machine
beyond exposing the already-computed `source` value, does NOT touch Phase
9's exit flow or Phase 7/8's fetch/snapshot logic itself.

</domain>

<decisions>
## Implementation Decisions

### Placement & persistence
- **D-01:** Session-wide, all 3 screens. Once `resolveVerbs()` resolves with
  `source: "local"`, show the indicator on Setup, Quiz, and Results for the
  rest of the app session (not just during the quiz that triggered it) —
  matches FETCH-05's original wording ("when running on the local
  fallback"). Simplest to wire: expose `source` once at the point
  `resolveVerbs()`/`prefetch()` resolves (Phase 7), read it wherever needed.

### Visual style
- **D-02:** Small neutral pill/badge — NOT a full-width banner. Use the
  existing `colors.secondary` background + `colors.textSecondary` text
  tokens from `src/theme/tokens.ts` (Phase 10) — reads as informational,
  explicitly distinct from `colors.error`/red error styling. Low visual
  weight, consistent with this being a "polish" pass, not a new prominent UI
  element.

### Copy wording
- **D-03:** Exact text: **"Using saved content"** (not "Offline content") —
  deliberately avoids implying the device itself is offline, since the
  backend could be unreachable/slow while the device has a live connection.

### Claude's Discretion
- Exact pill placement within each screen's existing layout (e.g. top of
  Setup's body vs inside the native header area) — implementation detail,
  should feel natural alongside Phase 10's existing header/token layout.
- Where in the codebase `source`/`VerbSource` gets threaded from
  `resolveVerbs()` into UI-readable state — e.g. a new field on
  `useQuizStore` (natural fit — the store already calls `resolveVerbs()` in
  `startQuiz()`) vs a separate lightweight module-level export from
  `src/dataset/source.ts` read directly by screens. Claude picks based on
  what's cleanest given the existing `cachedResult` memoization pattern.
  Must NOT require a second `resolveVerbs()` call or duplicate the
  fetch/fallback logic.
- Whether the indicator should also account for `prefetch()` (fired at app
  launch, before any screen mounts) resolving to `"local"` before the user
  even reaches Setup, vs only reflecting the source used by the most recent
  `startQuiz()` call — Claude decides based on what's simplest without
  introducing a race or stale-value bug. Either reading satisfies D-01's
  "session-wide once fallback is detected" intent.
- Exact icon/decoration (if any) inside the pill — text-only is sufficient
  per D-03's copy choice; an icon is optional polish, not required.

</decisions>

  the indicator (D-01). Each already imports from `../src/theme/tokens`

  pattern, not introduce a new styling approach.

<code_context>
## Existing Code Insights

### Reusable Assets
- `VerbSource` type (`"remote" | "local"`) already exists and is exported
  from `src/dataset/source.ts` — no new type needed, just needs to be
  threaded through to the UI layer.
- `src/theme/tokens.ts` — reuse directly, no new tokens needed for a
  neutral/secondary-styled pill.

### Established Patterns
- All 3 screens already import tokens and use `StyleSheet.create` with
  token references (Phase 10 pattern) — the new pill component/style should
  follow this exact convention, not introduce a separate styling approach.
- `useQuizStore` already threads async-resolved data (`resolveVerbs()`'s
  `verbs`) into store state inside `startQuiz()` — the same call site is the
  natural place to also capture `source` without a second network/resolve
  call.

### Integration Points
- `src/dataset/source.ts` → `useQuizStore.ts` (or wherever Claude decides to
  surface `source`) → all 3 screen components reading that state to
  conditionally render the pill.

</code_context>
