## Summary

No blockers. The pill's trigger logic, styling, copy, and per-screen placement all match the UI-SPEC contract, and `resolveVerbs()`'s existing module-level memoization (`cachedResult`, from Phase 07-01) means each screen's independent `OfflinePill` instance converges on the same `source` value without triggering duplicate fetches — so the D-01 "session-wide once triggered" persistence requirement holds correctly even though each screen mounts its own component instance rather than sharing one via the store. Findings below are quality/robustness gaps, not correctness bugs.

## Findings

### WARNING — Deviates from UI-SPEC's recommended integration pattern
`src/components/OfflinePill.tsx:19` (`resolveVerbs()` called directly), used identically in `app/index.tsx:60`, `app/quiz.tsx:108`, `app/results.tsx:88`.

The UI-SPEC's "Integration note" explicitly offers two sanctioned approaches: (a) capture `source` in `useQuizStore.startQuiz()` (which already awaits `resolveVerbs()` and today discards the `source` field), or (b) a lightweight module-level read of the already-resolved `cachedResult` in `source.ts`. It also says "do not call `resolveVerbs()` a second time." The implementation instead calls `resolveVerbs()` independently from three separate component instances (once per screen mount). Functionally this is safe today only because `resolveVerbs()` happens to memoize via `cachedResult` — but that safety is an implementation detail of a module the pill's author didn't need to re-verify by inspection to get this "right." A future change to `resolveVerbs()` (e.g. adding per-call side effects, telemetry, or removing memoization) would silently break the pill's cheap-call assumption for all three screens at once. Recommend routing this through the store per option (a), consistent with the spec's guidance, or wrapping (b) at least in a code comment that flags the dependency on `source.ts`'s memoization contract.

### WARNING — No test coverage for the component's actual render/mount path
`__tests__/offline-pill.test.ts` only exercises the two pure exports (`isLocalSource`, `OFFLINE_PILL_TEXT`). Nothing exercises `OfflinePill()` itself: the `useEffect` → `resolveVerbs()` → `setSource` → conditional render path, the cleanup guard (`active` flag preventing a post-unmount `setState`), or the "renders null while unresolved / renders null when remote" branches. Given this is a new UI component with actual runtime logic (an effect, a cancellation guard, a conditional render), a pure-function-only test suite provides no regression protection for the parts most likely to break (e.g. if the cleanup guard were accidentally removed, or the effect dependency array changed). Since the project's stack explicitly avoids `@testing-library/react-native` for pure-logic modules but does allow it "if a later phase decides to test a component's interaction logic" (per PROJECT.md), this component crosses that line — it has state and an effect, not just pure logic. Consider at minimum one test that mocks `resolveVerbs()` and asserts render output.

### WARNING — Cleanup guard (`active` flag) is untested and its only purpose is masked by memoization
`src/components/OfflinePill.tsx:18,24-26` — the `active`/cleanup-on-unmount guard is good practice (React warns on `setState` after unmount) but under the current test suite and manual QA there's no scenario that actually exercises unmount-before-resolve, since `resolveVerbs()`'s cached promise typically resolves near-instantly on repeat calls after the first screen. This means the guard's correctness has never been observed to matter in practice; it's silently trusted. Not a bug, but worth a comment or test noting *why* it's there, since a future refactor could remove it without any test failing.

### INFO — No accessibility role/label on the pill
`src/components/OfflinePill.tsx:34-36` — the `View`/`Text` pair has no `accessibilityRole` or `accessibilityLabel`. This is consistent with the rest of the codebase (grepped `app/*.tsx` and `src/components/` — zero existing usages of `accessibilityRole`/`accessibilityLabel` anywhere), so it's not a regression introduced by this phase, just a pre-existing gap that a new user-facing informational element inherits. Low priority; flagging for awareness only.

### INFO — `.then()` without `.catch()` on `resolveVerbs()` relies on an invariant from a different module
`src/components/OfflinePill.tsx:19-23` — `resolveVerbs().then(...)` has no rejection handler. This is currently safe because `src/dataset/source.ts`'s internal `resolve()` catches all fetch/parse errors and always falls back to `{ source: "local" }` rather than rejecting — so the promise returned by `resolveVerbs()` can never reject as currently written. This is correct today but is an implicit cross-module invariant with no local safeguard or comment in `OfflinePill.tsx` documenting the assumption. If `source.ts` is ever changed to let some error class propagate (e.g. a deliberate hard-failure path), this component would produce an unhandled promise rejection silently swallowed by the RN error handler, and the pill would just never appear — no crash, but a silent regression that would be hard to trace back to this file.

### INFO — Minor JSX indentation inconsistency in `app/index.tsx`
`app/index.tsx:59-117` — the children of the outer `<View style={[styles.container, ...]}>` (added `<OfflinePill />` at line 60 plus all pre-existing JSX through line 116) are indented one level shallower than the surrounding `<>...</>` and `<Stack.Screen>` siblings, suggesting the wrapping `<View>` tag's own indentation wasn't adjusted when `OfflinePill` was inserted as the first child. Purely cosmetic (verified no logic/paren mismatch), but worth a formatter pass — `expo lint`/prettier could not be run in this environment (missing `eslint.config.js`) to confirm auto-fixability.
