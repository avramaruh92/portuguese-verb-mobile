<objective>
Confirm the real live endpoint's response shape matches the contract the app
validates against — the one assumption (A1 / research Pitfall 4) that could not
be verified from the research/planning sandbox (no outbound network).

Purpose: FETCH-01's value ("actually fetches remote data") is only observably
exercised if the live payload passes `validateDataset()`. A field-name/casing
mismatch (e.g. snake_case) would make the app silently fall back to local
forever — safe by design (FETCH-03), but it would mean the remote path never
runs. This checkpoint catches that drift explicitly rather than letting it hide
behind the safe fallback.
Output: a confirmed (or flagged) match between the live contract and the app's
schema. No production code changes.
</objective>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 1: Live endpoint contract smoke check</name>
  <what-built>
    Plan 07-01 built `fetchRemoteVerbs()`, which validates the live payload with
    `validateDataset()` before accepting it. This checkpoint confirms the live
    endpoint's actual shape passes that validation, since it was never verifiable
    from the planning sandbox (A1 / research Pitfall 4).
  </what-built>
  <how-to-verify>
    Automation first (executor runs this, do not ask the human to do it manually):
    1. Fetch the live endpoint and inspect the raw shape:
       `curl -s https://portuguese-verb-api.onrender.com/content/verbs | head -c 2000`
       (This is a cold-start Render service — allow up to ~60s on first hit; retry once if it times out.)
    2. Confirm the top-level response is `{ "verbs": [ ... ] }` (an object with a `verbs` array, not a bare array).
    3. Confirm the first verb entry has exactly the keys `verb`, `translation`, `isIrregular`, `conjugations`
       (camelCase `isIrregular`, NOT `is_irregular`), and that `conjugations` has the four tense keys
       `present_indicative`, `preterite`, `imperfect`, `future`, each with the six subject keys
       `eu`, `tu`, `ele_ela`, `nos`, `voces`, `eles_elas`, all mapping to non-empty strings.
    4. Report the observed top-level keys and one full verb entry's key structure.

    Then the human confirms the observed shape matches src/dataset/types.ts / src/dataset/validate.ts.
    If any field name/casing differs, that is contract drift: the app will correctly fall back to local
    (safe), but flag it as a follow-up cross-repo reconciliation item — do NOT hand-edit validate.ts to
    match a drifting backend without a decision.
    If the endpoint is unreachable from this environment, report that explicitly; the human can run the
    curl on their own machine/simulator and paste the result.
  </how-to-verify>
  <acceptance_criteria>
    - The live response top-level shape (`{ verbs: [...] }`) and first-entry field names/casing are reported
    - The reported shape is confirmed by the human to match src/dataset/types.ts (or any drift is logged as a follow-up item)
  </acceptance_criteria>
  <resume-signal>Type "approved" if the live shape matches, or describe the drift observed.</resume-signal>
</task>
