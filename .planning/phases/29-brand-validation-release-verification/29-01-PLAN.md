  <action>
Create `scripts/validate-brand.ts` as a plain node-runnable TypeScript script
(no shebang, no CLI framework, no arg parsing), importing only `readFileSync`
and `existsSync` from `node:fs` and the default export from `sharp`.

Declare module-level constants before any function, grouped generator-style:
`APP_JSON_PATH = "app.json"`, `GENERATOR_PATH = "scripts/generate-brand-assets.ts"`,
then the five asset path constants (`ICON_PATH`, `FAVICON_PATH`, `SPLASH_PATH`,
`ANDROID_FOREGROUND_PATH`, `ANDROID_MONOCHROME_PATH`) pointing at
`assets/images/{icon,favicon,splash-icon,android-icon-foreground,android-icon-monochrome}.png`,
then dimension constants `CANVAS_PX = 1024` and `FAVICON_PX = 48`, then
`EXPECTED_BRAND_BG_HEX = "#FFF9F6"`, then
`FORBIDDEN_HEXES = ["#208AEF", "#E6F4FE"]`, then
`ALLOWED_SVG_SOURCE = "assets/brand/lafa-icon.svg"` and
`RETIRED_BRAND_ASSETS` listing the four retired paths from the
`<interfaces>` block. Per D-03 these literals are declared independently here
and MUST NOT be imported from `generate-brand-assets.ts` — the validator has to
assert against known-good/known-bad values without trusting the generator.

Define a `CheckResult` interface matching preflight's, with `expected` widened
to `number | string`. Then define check functions, each returning
`Promise<CheckResult>` or `CheckResult` and never throwing out to `main()`
(wrap any `sharp`/fs access in try/catch and return
`{ ok: false, actual: "error: <message>" }` on failure, the way preflight's
`checkStatus` handles a rejected fetch):

1. `checkPngDimensions(label, path, expectedWidth, expectedHeight)` — reads
   `await sharp(path).metadata()` (D-02: sharp metadata, never a `sips`
   shell-out), compares a `"{width}x{height}"` string.
2. `checkNoAlpha(label, path)` — asserts `metadata.hasAlpha === false`.
3. `checkForbiddenHexAbsent()` — reads `app.json` as raw text via `readFileSync`
   and asserts no case-insensitive occurrence of any entry in `FORBIDDEN_HEXES`;
   report the offending hex in `actual` when found.
4. `checkAdaptiveBackground()` — `JSON.parse`s `app.json` and asserts
   `expo.android.adaptiveIcon.backgroundColor === EXPECTED_BRAND_BG_HEX`.
5. `checkSplashBackground()` — locates the `expo-splash-screen` entry inside
   `expo.plugins` (it is a `[name, config]` tuple, not a bare string) and
   asserts its config `backgroundColor === EXPECTED_BRAND_BG_HEX` and its
   `image === "./assets/images/splash-icon.png"`.
6. `checkReferencedAssetsExist()` — for each of `expo.icon`,
   `expo.web.favicon`, `expo.android.adaptiveIcon.foregroundImage`,
   `expo.android.adaptiveIcon.monochromeImage`, and the splash plugin `image`,
   strip the leading `./` and assert `existsSync` on the resulting path. Emit
   one `CheckResult` per referenced asset so a single run names every broken
   reference.
7. `checkGeneratorSource()` — reads `scripts/generate-brand-assets.ts` as text
   and asserts it contains `ALLOWED_SVG_SOURCE`.
8. `checkGeneratorHasNoRetiredRefs()` — asserts the same generator text contains
   none of the `RETIRED_BRAND_ASSETS` basenames, and that none of those four
   files exist on disk (`existsSync` must be false for each). One
   `CheckResult` per retired asset is fine.

`main()` awaits all checks into a flat `results` array covering, at minimum:
icon 1024x1024, icon no-alpha, favicon 48x48, splash-icon 1024x1024,
android-icon-foreground 1024x1024, android-icon-monochrome 1024x1024, forbidden
hex absence, adaptive background, splash background+image, each referenced
asset's existence, generator allowed-source presence, and each retired-asset
absence. Log `PASS`/`FAIL` lines and the `{passed}/{total} checks passed`
summary exactly as preflight does, then `process.exit(1)` if any check failed
(D-01: non-zero exit so it works as a pre-flight gate). End the file with a bare
`main();`.

Use `const`/named functions only — no default export, matching project
convention. Respect `noUncheckedIndexedAccess`: guard or `??`-default any
indexed access into the parsed `app.json` plugins array rather than adding
unchecked casts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo files → validator script | `app.json`, `scripts/generate-brand-assets.ts`, and five PNGs are read as untrusted-shape input by `validate-brand.ts` (may be malformed JSON, missing, or wrong-typed) |
| validator → developer/CI decision | The script's exit code is the sole signal a human or pre-flight gate acts on |

Not in scope for this plan: no network calls, no auth, no user data, no secrets, no runtime app code. The script runs on a developer machine against local files only.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-01 | Tampering | `validate-brand.ts` trusting generator constants | mitigate | D-03: forbidden/expected hex and dimension literals are declared independently in the validator; assertion that `generate-brand-assets.ts` is never imported (Task 1 acceptance criteria) |
| T-29-02 | Denial of Service | validator crashing on a malformed/missing input file | mitigate | Every check function try/catches fs + `sharp` access and returns `{ ok: false, actual: "error: ..." }` instead of throwing — one run surfaces every failure |
| T-29-03 | Repudiation | a failing check being silently ignored | mitigate | `process.exit(1)` on any failure plus an explicit `{passed}/{total}` summary line; Task 2 empirically proves the non-zero fail path |
| T-29-04 | Elevation of Privilege | script executing repo content | accept | The script only reads files as text/PNG bytes; it never `eval`s, never spawns a shell, and never imports the generator — no execution path from repo data to code |
| T-29-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages are installed by this plan — `sharp@^0.35.3` is an existing devDependency already used by `scripts/generate-brand-assets.ts`. If any task would require `npm install` of a new package, stop and escalate for a legitimacy checkpoint |
</threat_model>
