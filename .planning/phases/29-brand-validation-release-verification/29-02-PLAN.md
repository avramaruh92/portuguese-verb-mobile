<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local repo → EAS build service | `eas build` uploads the project to Expo's cloud build infrastructure and receives back a signed IPA |
| EAS install URL → developer device | An internal-distribution build is installed on a real device from a public-ish URL |
| developer observation → planning record | The human's verdict is the only evidence backing VALID-03 |

Not in scope: this plan adds a Markdown planning artifact and runs an existing, already-configured build pipeline. It writes no application code.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-05 | Information Disclosure | EAS internal-distribution install URL | accept | `preview` uses `distribution: "internal"` (D-04) — the app contains no secrets, no auth, and no user data; the same posture already shipped in v0.5 |
| T-29-06 | Spoofing | verifying the wrong artifact (Expo Go / dev client / stale build) | mitigate | HUMAN-UAT.md records the specific build ID and expo.dev URL (Task 2) and its first section explicitly requires the EAS `preview` build, not Expo Go or a dev client |
| T-29-07 | Repudiation | sign-off recorded without the checks actually being run | mitigate | D-07: dated `APPROVED by developer` status line plus per-section numbered steps and a bulleted acceptance list; the developer's literal response is quoted in the SUMMARY |
| T-29-08 | Tampering | credentials misuse during an interactive `eas build` auth prompt | mitigate | Task 2 halts and surfaces an auth checkpoint instead of supplying or altering credentials non-interactively |
| T-29-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed by this plan — `eas-cli@^21.1.0` is an existing devDependency. Any new install requires a blocking legitimacy checkpoint |
</threat_model>
