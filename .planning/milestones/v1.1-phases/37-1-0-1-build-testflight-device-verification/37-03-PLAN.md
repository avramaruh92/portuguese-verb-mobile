<interfaces>
App facts the device steps rely on (verified during planning):
- Offline pill text: OFFLINE_PILL_TEXT = "Using saved content" (src/components/OfflinePill.tsx).
- "Report a problem" button is on the quiz screen (app/quiz.tsx) and opens a modal titled "Report a problem" with a submit button "Submit feedback". On server/network error it shows "Retry submission" (src/feedback/ReportFeedbackModal.tsx). The success state is shown only on HTTP 201 (src/feedback/submit.ts maps 201 to success, 400 to validation-error, other to server-error, throw/abort to network-error).
- "Help us improve" link is on the setup screen (app/index.tsx), the quiz screen and the results screen. It opens a modal titled "Send feedback" with placeholder "What's on your mind?", submit "Submit feedback", and on error "Retry submission" (src/productFeedback/ProductFeedbackModal.tsx). Same 201-means-success mapping.
- Timeouts (Phase 36): content fetch 15s, feedback and product feedback 45s. In airplane mode fetch fails immediately with a network error, so no long wait is expected.
- Dataset source is resolved once per JS process and cached. After a local fallback, a background retry (Phase 36 WR-01) may switch the NEXT resolution back to remote once the network returns. So the airplane-mode test must cold-start the app (swipe it away) with airplane mode already ON, and keep airplane mode on for the whole test.
- Backend (sibling repo portuguese-verb-backend): tables feedback_reports and product_feedback_reports, both with columns id, "appVersion", "createdAt". Fastify runs with disableRequestLogging: true, and GET /content/verbs does not info-log per request. So the Frankfurt app log stream may NOT show the content request line. Evidence for E2E-01 must therefore come from Render's dashboard for portuguese-verb-api-fra: the HTTP request log view (filter path /content/verbs) if available, or the Metrics HTTP requests graph at the test minute. The POST /feedback and /product-feedback handlers DO req.log.info, so those requests appear in the service log stream.
- The mobile app never holds DB credentials. Row checks are done by the developer in the Supabase SQL editor.
</interfaces>
