## Summary

This phase has one real technical risk (the D-09 backend data-retention question) and otherwise consists of copywriting, static-page hosting, one config-key addition, manual screenshot capture, and re-running an already-proven build/submit pipeline. The critical open item is resolved by this research: **the backend's Fastify server logs client IP addresses by default, for every request, via its unmodified built-in request logger** — this was not previously verified and changes the confidence (though probably not the final answer) behind D-07/D-08.

The GitHub Pages hosting path (D-01) requires enabling Pages via the repo settings or GitHub API — it is not yet enabled (`gh api repos/.../pages` returns 404) — and a `/docs` folder with two static HTML files. The age rating questionnaire has materially changed in 2026 (new 16+ tier, mandatory in-app-controls/medical/violence questions, and — as of September 2026 — mandatory social-media questions), so the CONTEXT.md's "likely 4+" assumption should still hold for this app but the questionnaire itself will look different from what a developer might remember. `eas submit`'s existing config (`ascAppId` only, no API key fields) relies on EAS CLI's interactive Apple ID login flow, which already succeeded once in Phase 24 — no new App Store Connect API key setup is strictly required. `app.json`'s `ios` block has no `supportsTablet` key today, confirming STORE-05's premise.

**Primary recommendation:** Resolve D-09 by flagging to the user, before finalizing the privacy label, that the backend's default Fastify logger captures request IPs — and recommend a trivial one-line backend fix (`disableRequestLogging: true` or a custom serializer omitting `remoteAddress`) as a pre-submission action item in the sibling repo, while documenting a defensible fallback answer if that fix isn't made. Everything else in this phase can proceed exactly as scoped in CONTEXT.md's decisions.

## Backend Data-Retention Investigation (resolves D-09)

**This is the most important finding in this research.**

### Investigation method
Direct source inspection of the sibling repo `/Users/avi/portuguese-verb/portuguese-verb-backend` (Fastify + Prisma + Supabase Postgres, deployed to Render).

### Findings

1. **No IP address, user agent, or any request-metadata field is persisted to the database.** `prisma/schema.prisma`'s `FeedbackReport` and `ProductFeedbackReport` models contain only the documented contract fields (`message`, `verb`/`category`, `tense`/`screen`, `subject`, `correctAnswer`, `selectedAnswer`/none, `appVersion`, `platform`, `createdAt`) — no `ip`, `ipAddress`, `userAgent`, or `remoteAddress` column exists anywhere in the schema. `[VERIFIED: sibling repo source, prisma/schema.prisma]`

2. **The route handlers' explicit application-level logging also does not include IP.** `src/routes/feedback/routes.ts` and `src/routes/product-feedback/routes.ts` each call `req.log.info({ id, verb/category, tense/screen, subject, platform, appVersion, outcome }, "...")` — a deliberately curated field list that excludes any client-identifying data. `[VERIFIED: sibling repo source]`

3. **However, `src/app.ts` initializes Fastify with `Fastify({ logger: true })` and no `disableRequestLogging` override, no custom `serializers` override, and no `onRequest`/`onResponse` hook suppressing logging.** Fastify's built-in log-controller (`node_modules/fastify/lib/log-controller.js`) defaults `disableRequestLogging` to `false` and unconditionally logs `request.log.info({ req: request }, 'incoming request')` on every single request (feedback POST, product-feedback POST, **and** the `GET /content/verbs` call) — this happens automatically, is not something the app author wrote, and is easy to miss when auditing only the app's own log calls. `[VERIFIED: sibling repo node_modules/fastify/lib/log-controller.js, sibling repo src/app.ts]`

4. **Fastify's default request serializer explicitly includes the client IP.** `node_modules/fastify/lib/logger-pino.js`'s `serializers.req` function returns `{ method, url, version, host, remoteAddress: req.ip, remotePort }` — `remoteAddress: req.ip` is the literal line. This is the exact serializer used by the "incoming request" log line from finding #3, since no custom serializer override exists in this codebase. `[VERIFIED: sibling repo node_modules/fastify/lib/logger-pino.js:53]`

5. **No third-party logging/analytics/observability SDK is present.** Grepped for Sentry, Datadog, Logtail, LogDNA, Papertrail, and generic "analytics" across the backend's source and config — zero matches. `render.yaml` configures no log-streaming add-on. `[VERIFIED: sibling repo grep, render.yaml]`
   - Logs go only to stdout, captured by Render's platform log stream. Render's own documentation states it retains "the last 1000 lines" of logs by default on lower tiers, with older entries expiring/rolling off (exact day-based retention for the free plan is not explicitly published in Render's docs as of this research — `[CITED: render.com/docs/logging, community.render.com thread on retention]`, MEDIUM confidence on exact retention window, but HIGH confidence that it is a short, rolling, non-queryable-by-default window, not a permanent or exportable store).

### What this means for D-07/D-08/D-09

The backend does **not** store IP addresses in its database, and does **not** intentionally log or use IP addresses for any purpose (no fraud detection, no analytics, no fingerprinting) — this part of the original assumption holds. However, the assumption that "standard ephemeral server request logs don't count as collection" was previously **unverified** and is now **verified true in the specific sense that**: the IP capture is an unmodified framework default (Fastify's built-in request logger), routed only to Render's short-lived rolling platform log stream, never persisted to the app's own database, never exported to any third-party service, and never used for any product purpose.

Apple's own App Privacy guidance draws a distinction for IP addresses collected "only to complete a network request" and not stored for other purposes — this backend's behavior sits close to, but not perfectly inside, that exception, because the IP genuinely does appear in a log line (even if that log line is short-lived platform infrastructure logging rather than app-controlled storage).

**Recommendation (two options, present both to the user):**

- **Option A (recommended, low-cost):** Before the real submission build, make a trivial one-line change in the sibling backend repo: add `disableRequestLogging: true` to the `Fastify({...})` options in `src/app.ts`, or add a custom `req` serializer that omits `remoteAddress`. This removes the ambiguity entirely and makes D-07/D-08 unconditionally accurate with zero interpretive judgment required. This is a backend-repo change and technically outside this mobile phase's file scope — flag it to the user as a pre-submission checklist item (not a Phase 35 task against this repo, since `portuguese-verb-api` is a separate repo/deploy), or as a `checkpoint:human-verify` reminder in the plan.
- **Option B (fallback, if Option A isn't done before submission):** Keep D-07/D-08 as currently decided (User Content / Not Linked to You, Data Not Collected respectively) — this remains defensible given the IP is never persisted to the database, never exported, and only appears in a short-lived, non-queryable platform log stream — but document this reasoning explicitly in `store/privacy/nutrition-label-answers.md` so the judgment call is auditable, not silent.

Either way, **D-09 is now answered**: the backend does not retain IP addresses in any durable, queryable, app-controlled store. The only place IPs briefly appear is Render's own platform-level request logging, which is infrastructure-level, not something `portuguese-verb-api`'s code deliberately implements or can be blamed for under the "data collected by the app" framing Apple uses — but Option A is the cleaner, fully unambiguous fix and costs one line.

## Age Rating Questionnaire (2026)

Apple materially overhauled the age rating system in 2026, effective for a hard deadline of **January 31, 2026** (already passed relative to this research date of 2026-08-16, meaning the new questionnaire is now the only path — there is no legacy fallback to check against).

**What changed:**
- Rating tiers expanded from the old 4/9/12/17 system to **4+, 9+, 13+, 16+, 18+** — a new 16+ tier was added to separate "mature themes" from full 18+ adult content. `[CITED: developer.apple.com/news/?id=ks775ehf]`
- The questionnaire now includes new mandatory questions on **in-app controls/capabilities**, **medical or wellness topics**, and **violent themes** — these are new question categories that didn't exist in the pre-2026 questionnaire. `[CITED: developer.apple.com/news, 9to5mac.com 2026-07-09 article]`
- As of **September 2026**, a further mandatory **social media questions** section is being added, specifically targeting apps with "the ability to redistribute, amplify, or interact with user-generated content through a social feed or similar discovery method." `[CITED: developer.apple.com/news/?id=tlur8uvi]` — this does not apply to Lafa (no social feed, no UGC redistribution, no discovery mechanism), but the planner should note the questionnaire may present this section regardless and it should be answered "No" across the board.

**Assessment for this app:** Lafa has no user-generated public content, no ads, no in-app purchases, no web browser access (`expo-web-browser` is installed as a dependency but not used for arbitrary browsing in the current UI — verify at execution time it's not exposing an open browsing surface), no chat/messaging, no location data, and no medical/wellness claims. The CONTEXT.md's "likely 4+" assumption remains reasonable `[ASSUMED — training-data + general-guidance based, not verified against the live questionnaire's exact new wording]`, but per CONTEXT.md's own caveat and this research's confirmation that the questionnaire structure changed materially in 2026, **the actual questionnaire must be walked live in App Store Connect at execution time** — do not pre-fill answers in `store/` without doing so, since the new question categories (medical/wellness, violent themes, in-app controls) don't map cleanly onto the old questionnaire's mental model and skipping the live walkthrough risks an inaccurate rating.

### Anti-Patterns to Avoid
- **Assuming "no explicit app-level logging code" means "no data collection":** This research's central finding is exactly this trap — the app's own route handlers deliberately log a curated, safe field set, but the framework's *default* behavior (Fastify's built-in request logger) captures more than the app code shows. Always check framework defaults, not just application code, when auditing data flows for a privacy label.
- **Pre-filling the age rating questionnaire from memory/training data:** The 2026 questionnaire has new mandatory sections (medical/wellness, violent themes, in-app controls, soon social media) that don't map onto older mental models of "the age rating form." Walk it live.
- **Treating GitHub Pages as already-enabled infrastructure:** It is not — `gh api .../pages` returned 404 in this session. Budget the enable + propagation-delay step explicitly, don't assume "push to `/docs`" alone makes the URL live.

## Common Pitfalls

### Pitfall 1: Treating the privacy label as a documentation-only task with no cross-repo verification
**What goes wrong:** Assuming the mobile app's own request payloads are the complete picture of "what data is collected," when the server side (a separate repo, separate deploy) may capture more via framework defaults.
**Why it happens:** The mobile codebase genuinely doesn't send extra fields — the temptation is to stop the audit there since "the mobile side is all I control."
**How to avoid:** Always check the receiving server's actual logging/persistence behavior, including framework defaults (this research's `Fastify({ logger: true })` finding), not just the request contract.
**Warning signs:** A nutrition label answer that reads suspiciously clean ("Data Not Collected") for every single network call in an app that talks to a real backend — that's a signal to verify, not a green light to accept at face value.

### Pitfall 2: Assuming GitHub Pages is "just pushing to a folder"
**What goes wrong:** Pushing `docs/*.html` to `main` and then entering the expected `github.io` URL into App Store Connect before Pages is actually enabled/deployed — the URL 404s, and Apple's URL-reachability check (if/when it runs) fails.
**Why it happens:** GitHub Pages requires an explicit enable step (Settings toggle or API call) even after the folder exists in the branch; this is easy to forget since many other static-hosting platforms auto-detect and deploy on push.
**How to avoid:** Explicitly enable Pages (verified in this research: currently disabled) and verify both URLs return `200` before entering them anywhere in App Store Connect.
**Warning signs:** `gh api repos/.../pages` returning 404 (exactly what this research found).

### Pitfall 3: Walking the age rating questionnaire from memory of the pre-2026 form
**What goes wrong:** Answering based on a mental model of the old 4/9/12/17 questionnaire, missing the new mandatory medical/wellness, violent-themes, in-app-controls, and (from September 2026) social-media question blocks.
**Why it happens:** The overhaul happened recently (deadline was 2026-01-31) and the questionnaire's shape changed non-trivially, not just its output tiers.
**How to avoid:** Walk the live questionnaire at execution time, answer each new section explicitly (all should resolve to "No"/"None" for this app), don't assume the old outcome (4+) carries over automatically without re-answering every question.
**Warning signs:** A plan or `store/` file that states a final age rating without evidence of having walked through category-by-category live questions.

### Pitfall 4: Assuming `eas submit` needs new App Store Connect API key setup
**What goes wrong:** Spending time creating a `.p8` API key and wiring `ascApiKeyPath`/`ascApiKeyIssuerId`/`ascApiKeyId` into `eas.json` when the existing interactive-auth flow (already proven in Phase 24) still works fine for a single, human-attended submission.
**Why it happens:** Some EAS documentation and tutorials default to recommending API keys as the "modern"/CI-friendly path, which can read as a requirement rather than an option.
**How to avoid:** Confirm the existing `ascAppId`-only config (no API key fields) is sufficient for one interactive submission — it is, per this research — and only add API key config if a future phase needs unattended/CI submission.
**Warning signs:** None currently — this is a preventive note, not a live blocker.
